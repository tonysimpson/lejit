36. **Compile-time C calls (libffi): cost and reach.** `ni/x64/iencoding.c:compile_time_call` folds `CfPure` helpers with constant arguments through libffi (`var_call`), calling `ffi_prep_cif` on every call, with `long` and `double` arguments only (anything else aborts). 37. **Generate the x64 encoder from its `@asm` annotations.** Owner wants to explore it, only after robust compile-time metrics exist (QUESTIONS 35). Idea (owner and Claude independently): the `@asm` intent is the source of truth; a generator assembles it with `llvm-mc --show-encoding`, whose fixups give each immediate's and displacement's offset and width, and assembles once per register to find the REX/ModRM bits. It writes a checked-in header, stale-checked as in D24, so the source release needs no generator. Value-dependent size choice (disp8/disp32, imm8/imm32, short/near jumps) stays a small hand-written rule, the place past encoder bugs were (B1). DynASM was considered and rejected: its run-time action-list interpreter and two-pass encode don't fit emit-then-patch and cost compile speed (D29). `v_mem_mov.h` has no annotations yet. [run] (llvm-mc fixups), [inferred]
38. **Where else do two forms of one value split merge points?** Answered (`e823ee8`, D41, CODE_SIZE.md, Two forms of one value). Measured over the 23 pyperformance benchmarks: blocks differing from an earlier one only in that local, large int constant against a virtual int 14, against a run-time int 2, virtual int against run-time int object 46, virtual float against run-time float 6, virtual empty list against run-time list 30 (of 2,367 blocks). A large int constant now becomes a run-time object from a merge point's second block (the same object, so identity is kept): pyflate −2.2% instructions compiled, all −0.2%. The other pairs are left to the cap: making the run-time object virtual loses identity, and computing the virtual is a respawn point a replay can't reach after the merge-point decision; an unreplayable experiment that computed them saved only 0.1% more. deltablue's `change` keeps its extra block: once 1050 and 2000 are run-time, it differs in `v`'s promoted type, a fixed fact.

40. **Virtual characters for str?** `s[i]` now gives CPython's cached one-character string (`punicodeobject.c`, D37), so `s[i] == 'c'` is still a `cimpl_unicode_eq` call and `ord(s[i])` a builtin call. Py2's `pstringobject.c` kept the character as a virtual one-char string whose code is a word, making both a byte compare. Worth it only with a string-heavy benchmark to measure it on: none in `tools/pyperformance/` is (PROFILE.md, str and bytes). The same question for run-time `in` with a one-character constant needle.
41. ~~Should load guards repair themselves like store guards (D39)?~~ Answered (`6cd0c26`, D60, STORES.md "Load guards"): built, cheaply, though on the 23 benchmarks no load guard fails in warm code because a class changed. The failures measured (`tools/loadguards.py`) were classes with a metaclass, which CPython 3.7 never gives a version tag, so their guard never passed (mdp: 3.2 M generic loads per iteration on `Fraction`), and loads from Enum classes. Ni now gives such classes a tag: mdp −10.8% instructions, the others unchanged. On `tools/load_micro.py`, a class constant set after compiling no longer leaves loads generic for good (4.4 → 1.0 ms per run); a class attribute bumped as a counter on every iteration still fails every guard (20.5 → 24.4 ms; plain CPython 42.6). The key is (type, name, the descriptor or class attribute found, or "generic" or "instance only"); the inline keys stay D31's per-site record.
42. **Should a respawned branch at a split site join the hit path's continuation?** Answered (`f229d14`, D44, CODE_SIZE.md "Respawned branches rejoin"): yes, through join points, the blocks a split already starts, listed per instruction. Asked on the inline-stores branch (`80a60ce`): a guarded site ends its block (`split_after_global`), and a branch respawned from one of its checks compiled the rest of the code as a new block, so a constructor whose checks fail one after another got a copy per failure (richards' `Task.__init__` 10 → 54 KB with inline stores, most of richards' +85% code). With joins it is 10.8 KB again. [run]

44. **Should a megamorphic version forget what it derives from the forgotten value?** Today the mark is on the type only; the attribute's value (a bound method, a function) is a new unmarked value that the next call promotes. Importing pkg_resources: 70 sites and 13.6 KB compiled downstream of 51 megamorphic versions (`doc/OPTION_D.md`). Forgetting it stops that, but makes a call generic where a site's methods are few (one base-class method for many subclasses, as in richards); a cache keyed on the descriptor rather than the type would keep both. Unmeasured for speed. [run]
45. **Can a callee be compiled at run time for a call cache?** Option D's CALL keyed on the code object needs an entry point compiled outside `psyco_call_pyfunc`, from the call site's frozen state, when a new function arrives. Unknown: finfo for frame reconstruction, the recursion depth (`DEFAULT_RECURSION`), the tracing test (D46), and whether the callee's argument state is really the same for every function there. [inferred]
46. **Should `codesize.py -D` attribute code compiled through pauses and respawns to the promotion value it came from?** `codesize.py -D` (`8081f96`) gives each value the code compiled in its own compile and in the sites it emitted, but code compiled later through a coding pause or respawn inside that continuation counts as a pause or respawn (unpack_sequence: the `tuple` copy shows 5 KB against `list`'s 120 KB). A pause or respawn record could carry the site and value it was emitted under, in `NI_CODESTATS` builds only. Matters only if option D is pursued. [run]
47. **Compute D53's cannot-block list instead of writing it?** `effects.py` finds 82 residual call sites that can't release the GIL but have neither `CfNoBlock` nor a place in `cannot_block_init`, so each is followed by an `eval_breaker` test it doesn't need. The list would become every function that doesn't reach `Py_BEGIN_ALLOW_THREADS`, less the ones that run Python for long. Measure first what those tests cost (instructions per warm iteration). (D71, METACOMPILER.md "Effect rules".)
48. **How does the core handle 3.8's finally opcodes without `#if`?** `mergepoints.c` and `pycompiler.c` name `SETUP_LOOP`, `SETUP_EXCEPT`, `BREAK_LOOP`, `CONTINUE_LOOP`, which 3.8's `opcode.h` doesn't define, and 3.8 adds `BEGIN_FINALLY`, `CALL_FINALLY`, `POP_FINALLY`, `END_ASYNC_FOR` with new stacks for `END_FINALLY` and `WITH_CLEANUP_*` (3.11 changes again, to exception tables). Options: a mechanism per bytecode model (`block_stack`: a detector on `Include/opcode.h`, a snippet with Ni's block-stack cases and analysis for each); or a generated header of which opcodes exist, tested by the core (a capability `#if`, which D67 may or may not allow). `PORT38.md` item 9.
49. **How does the policy table name a definition some sources don't have?** `policy.py` fails a key not in the source, so there is no entry for a 3.8-only function (`_PyErr_SetObject` as an effect seed, `PyVectorcall_Call`), and no version may be written (D67). Candidate: `None` in an entry's shape tuple meaning "absent in this source", checked like any shape, so a source that has the definition still needs its shape recorded. `PORT38.md` items 4 and 5.
