36. **Compile-time C calls (libffi): cost and reach.** `ni/x64/iencoding.c:compile_time_call` folds `CfPure` helpers with constant arguments through libffi (`var_call`), calling `ffi_prep_cif` on every call, with `long` and `double` arguments only (anything else aborts). To investigate: its share of compile time (QUESTIONS 35), and whether it needs extending, such as pointer arguments or more argument kinds, as more objects become virtual. Strings are the likely first case: folding `len`, slicing or comparison of constant strings. [read], [inferred]
37. **Generate the x64 encoder from its `@asm` annotations.** Owner wants to explore it, only after robust compile-time metrics exist (QUESTIONS 35). Idea (owner and Claude independently): the `@asm` intent is the source of truth; a generator assembles it with `llvm-mc --show-encoding`, whose fixups give each immediate's and displacement's offset and width, and assembles once per register to find the REX/ModRM bits. It writes a checked-in header, stale-checked as in D24, so the source release needs no generator. Value-dependent size choice (disp8/disp32, imm8/imm32, short/near jumps) stays a small hand-written rule, the place past encoder bugs were (B1). DynASM was considered and rejected: its run-time action-list interpreter and two-pass encode don't fit emit-then-patch and cost compile speed (D29). `v_mem_mov.h` has no annotations yet. [run] (llvm-mc fixups), [inferred]
38. **Where else do two forms of one value split merge points?** Answered (`e823ee8`, D41, CODE_SIZE.md, Two forms of one value). Measured over the 23 pyperformance benchmarks: blocks differing from an earlier one only in that local, large int constant against a virtual int 14, against a run-time int 2, virtual int against run-time int object 46, virtual float against run-time float 6, virtual empty list against run-time list 30 (of 2,367 blocks). A large int constant now becomes a run-time object from a merge point's second block (the same object, so identity is kept): pyflate −2.2% instructions compiled, all −0.2%. The other pairs are left to the cap: making the run-time object virtual loses identity, and computing the virtual is a respawn point a replay can't reach after the merge-point decision; an unreplayable experiment that computed them saved only 0.1% more. deltablue's `change` keeps its extra block: once 1050 and 2000 are run-time, it differs in `v`'s promoted type, a fixed fact.
39. **Attribute stores: which option, if any?** Partly answered: options 1 and 2 are done (D39, `e86f8ae`). Open: an inline store (option 3 or 4), which needs a choice for `ma_version_tag` (Ni's own counter, or finding CPython's static one).
40. **Virtual characters for str?** `s[i]` now gives CPython's cached one-character string (`punicodeobject.c`, D37), so `s[i] == 'c'` is still a `cimpl_unicode_eq` call and `ord(s[i])` a builtin call. Py2's `pstringobject.c` kept the character as a virtual one-char string whose code is a word, making both a byte compare. Worth it only with a string-heavy benchmark to measure it on: none in `tools/pyperformance/` is (PROFILE.md, str and bytes). The same question for run-time `in` with a one-character constant needle.
41. **Should load guards repair themselves like store guards (D39)?** `pobject.c:generic_getattr`'s per-site guard stays stale for good once its class changes, so a method compiled before a class constant is set keeps the generic path. Stores needed the repair (raytrace); for loads it is unmeasured. The kind of a load is more than one function (the descriptor, data or not, the inline keys), so the key would be larger.
