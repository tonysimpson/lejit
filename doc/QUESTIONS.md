## Design questions for the meta-compiler
(Q11 and Q24, on the target version, were answered by D17.)
7. **Per-slot meta signature:** for each type slot, which arguments are `vinfo_t*` (v) and which raw compile-time values (l)? It exists only implicitly at call sites today (PATTERNS P09). Where should this table live, and can it be derived?
8. **`Cf*` flags per CPython function:** how much can be derived from headers, docs or return types, and how much needs annotation (`CfPure` especially)?
9. **Restart safety** (PATTERNS rules §1): can a generator prove it, or must translated code be structured (for example "all promotions before any effects")?
10. **Virtual-object choices** (P18): annotation format? (Which constructors to virtualise, field layout, nested weights.)
26. **First meta-compiler target: virtual small integers on 3.7?** (owner's idea, 2026-11-16.) Generate the compile-time form of `Objects/longobject.c:long_add`/`long_sub`/`long_richcompare` from their one-digit fast paths (`MEDIUM_VALUE`): a virtual int held as a machine word, overflow check, fallback to the residual call (D13). Measurable (integer benchmarks are at about 2× now, all residual calls) and on a baseline that 50 CPython test modules check. 3.12's `_PyLong_Add` has the same shape (`_PyLong_IsCompact`), so it should carry over to D17. To settle: does this replace D19's stage order (descriptors first)? [inferred] **Owner chose ints as the first slice** (2026-11-16), limited to what the backend supports: + - * unary - comparisons, bool. Step 1, the hand-written reference, is `fdbaa88` (`ni/Objects/plongobject.c`). Steps 2–3 done (`64f88e7`): `tools/metac/gen_long.py` generates + - * unary - ~ from `Objects/longobject.c`; the result and what it couldn't do are in `METACOMPILER.md`. Open: the stage order question above, and whether the `Py_SIZE` rule for `long_bool` belongs in the generator or in the runtime model (QUESTIONS 23).
28. **Fixed-set promotion, generalised?** Upstream's `fixed_switch_t` (`9bd5834:c/codegen.h`, already disabled there) promoted a value only if it was in a given set, sending everything else down one default path. A promoted constant is held by the compiled code for good, so plain promotion of a class keeps it alive (KNOWN_BUGS F25). `96aaec2` added the one filter needed so far, `psyco_static_type_promotion` (only static types become constants; anything else takes the site's megamorphic version), used by the `isinstance` and `type_call` metas. Open: will the meta-compiler need other filters (a fixed set of values, "immortal objects" on 3.12+), and should `Psyco_NeedType` itself stop holding heap types? [inferred]
29. **Cached globals on 3.12+.** D25 guards on `ma_version_tag`, which 3.12 deprecates (PEP 699) and later versions may drop. 3.12's dict watchers (`PyDict_AddWatcher`) report changes instead: compiled code could test a per-site "still valid" flag that the watcher clears, with the same do_changed_global logic. Also: whether cached values should stop living for ever (they are compile-time constants, never released). 3.12 itself guards LOAD_GLOBAL on the keys version (`ma_keys->dk_version`) plus an entry index (METACOMPILER, bytecode desk read). [inferred]
30. **Use 3.12's specialised instruction families as hints?** Each family member (`BINARY_OP_ADD_INT`, `LOAD_ATTR_SLOT`, `CALL_NO_KW_ISINSTANCE`…) is a `DEOPT_IF` guard plus a fast path: the type cases CPython found worth specialising. Should the bytecode generator use them to choose which promotions and metas to emit, or derive everything from the generic instructions and the slot metas? (METACOMPILER, bytecode desk read.) [inferred]
31. **Enter compiled code on 3.12 through `PyFunction_SetVectorcall`?** PORT312.md recommends it over the PEP 523 hook, whose frame clean-up needs hidden CPython functions. It returns to upstream's proxy design. Install it on every function through a creation watcher, or only on hot ones? [run] for the prototype
32. **Compiled code and `sys.monitoring` / tracing on 3.12.** Compiled functions are invisible to `sys.setprofile` (the same as Ni on 3.7 today). Should Ni fall back to the interpreter while monitoring or tracing is active, as a debugger or coverage tool expects? [inferred]
33. **Compiled generator bodies, and the 3.12 hook.** GENERATORS.md option A compiles resumable bodies over the CPython frame. On 3.12 resumes bypass vectorcall, so A needs the PEP 523 hook (with `_PyInterpreterFrame`) just for generator frames. Is that acceptable, or should generators stay interpreted there, with only genexpr inlining (option B)?
34. **Attribute lookup specialised on the type (A9), branch `a9-getattr` `b6d8477`.** It's worth a lot [run], release build: richards 1.64→2.21×, deltablue 1.57→2.02×, go 1.55→1.90×, float 1.49→1.95×, chaos 1.95→2.15×, raytrace 1.16→1.30×. It follows `_PyObject_GenericGetAttrWithDict`, guarded by `tp_version_tag`. A method becomes a virtual bound method, so `obj.m()` is a direct compiled call. Not merged: `attributes.getattr_added_later` crashes. After `__getattr__` is added to the class, the failed guard jumps straight into code respawned earlier for the not-found error path; no new compile happens. Ruled out: the block split, an `int` versus `long` guard result, and the instance-dict branch. Next step: work out how respawn counts relate to the promotion continuation (`dispatcher.c:do_respawn`, `codemanager.c:new_code_buffer`). Was a site with two respawn points after a promotion ever exercised? Merging also needs a decision: the compiled code keeps a reference to each descriptor it specialised on, for good.
35. **How should compile time be measured?** D29 judges backend changes against compile time, and nothing measures it yet. Owner wants three-way benchmarks on realistic code: plain CPython, the first run (compiling), and later runs (compiled). Candidates: time spent in the compiler per benchmark run (pyperformance, bench.py), and code bytes emitted per millisecond. Also unmeasured: how much of richards and deltablue goes on compiled-to-compiled call sequences (arguments on the stack, every occupied register pushed), which decides whether a register calling convention is worth it. [inferred]
36. **Compile-time C calls (libffi): cost and reach.** `ni/x64/iencoding.c:compile_time_call` folds `CfPure` helpers with constant arguments through libffi (`var_call`), calling `ffi_prep_cif` on every call, with `long` and `double` arguments only (anything else aborts). To investigate: its share of compile time (QUESTIONS 35), and whether it needs extending, such as pointer arguments or more argument kinds, as more objects become virtual. Strings are the likely first case: folding `len`, slicing or comparison of constant strings. [read], [inferred]
37. **Generate the x64 encoder from its `@asm` annotations.** Owner wants to explore it, only after robust compile-time metrics exist (QUESTIONS 35). Idea (owner and Claude independently): the `@asm` intent is the source of truth; a generator assembles it with `llvm-mc --show-encoding`, whose fixups give each immediate's and displacement's offset and width, and assembles once per register to find the REX/ModRM bits. It writes a checked-in header, stale-checked as in D24, so the source release needs no generator. Value-dependent size choice (disp8/disp32, imm8/imm32, short/near jumps) stays a small hand-written rule, the place past encoder bugs were (B1). DynASM was considered and rejected: its run-time action-list interpreter and two-pass encode don't fit emit-then-patch and cost compile speed (D29). `v_mem_mov.h` has no annotations yet. [run] (llvm-mc fixups), [inferred]

## Decoupling the core (D16)
21. **Host data structures:** the core keeps snapshots, the meta table and promotion caches in CPython lists, dicts and capsules (`dispatcher.c`, `mergepoints.c`, `codemanager.c`). Should it replace them with its own C structures?
22. **Where `PsycoObject.pr` and the `LOC_*` slots go:** today the core state embeds Python frame state (`Python/pycheader.h`). What is the language-neutral interface: an opaque per-language payload plus callbacks for "compare", "snapshot" and "unwind"?
23. **Refcounting and object layout in the backend** (`x64/ipyencoding.h`): these should become generated "runtime-model" operations that the backend only emits. What is the minimal set (incref, decref plus dealloc call, type load, ...)?
25. **Psyco runtime helpers in translated files** (`psyfunc.c` has ~100 CPython API uses): which parts are core calling machinery and which are translated `call_function`/`_PyFunction_FastCall` logic?
